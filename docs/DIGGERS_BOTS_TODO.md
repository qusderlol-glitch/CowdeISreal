# Боты DiggersBtwModes — нужны исходные описания

> **Ни один бот DiggersBtwModes не найден и не перенесён.** Источники проверены (см. `PRODUCT_AUDIT.md`), упоминаний нет. Ничего ниже не утверждает, что такие боты существовали в таком виде.

## Что уже есть
- **Реестр команд** — `src/lib/commands.ts`: имя, описание, синтаксис, требуемое право, модуль (`bot_key`), флаг `example`.
- **Исполнение только на сервере** — `public.run_command(channel, text)` внутри `send_message`. Команда — фиксированная ветка SQL: нет `eval`, shell, сетевых вызовов, произвольного кода.
- **Проверки**: модуль включён в сообществе (`community_bots.enabled`), у автора есть право команды, общий лимит частоты сообщений + отдельный лимит команд (10 в минуту), ошибки возвращаются как ответ бота и пишутся в `bot_command_log`.
- **Модуль-пример `examples`** (помечен «пример», выключается в «Настройки сообщества → Боты», удаляется вместе с веткой в `run_command` и записями реестра): `/help`, `/rank`, `/top`, `/roll`, `/coin`. Это НЕ боты DiggersBtwModes.

## Что нужно от владельца для каждого бота
- Название и назначение.
- Список команд: синтаксис, аргументы, ответ.
- Кто может вызывать (какое право/роль).
- Какие данные бот хранит и как долго.
- Нужны ли внешние сервисы (API, ключи) — тогда исполнение переносится в Edge Function, ключи хранятся в Supabase Secrets.

## Как добавить модуль (адаптер)
1. `src/lib/commands.ts` — добавить записи `{ name, module: '<bot_key>', ... , example: false }`.
2. Новая миграция: в `public.bot_modules` вставить `('<bot_key>', 'Название', 'Описание', false)`; расширить `public.run_command` новой веткой `when '<bot_key>:<cmd>'`.
3. Если нужен внешний API — Edge Function `supabase/functions/bot-<bot_key>`, вызывается клиентом с JWT; функция сама проверяет права через RPC `has_channel_perm`.
4. Тест в `supabase/tests/` (позитивный вызов, вызов без права, выключенный модуль).
